# Donatix — Flutter и исходный сервер

Версия приложения: 1.0.0+4, Android/iOS identifier `tj.donatix.app`. Сервер по умолчанию: `https://donatix.tj`.

В этом комплекте приложение вызывает настоящие операции сервера из присланного проекта. Цена, баланс,
выдача, возврат, курсы, комиссия и права пользователей рассчитываются сервером. Локальных фиктивных
покупок и балансов в клиенте нет. Производственный запуск сервера запрещает MockSupplier.

Это комплект исходников с выполненными проверками, **не уже собранный и принятый Play-релиз**.
APK/AAB/IPA ещё не получены. iOS-настройки описаны в IOS_SETUP_RU.md. Границы проверки описаны в `RELEASE_STATUS.md`.

WebView-пакет удалён. Клиентские операции выполнены Flutter-виджетами. Административные и текстовые
страницы разбирают HTML сервера и строят Flutter-виджеты: формы отправляют оригинальные параметры
с CSRF, ссылки ведут в исходные действия. Стили и основные движения админки реализованы нативными компонентами; HTML используется как транспорт существующих данных и форм. Полного CSS/JavaScript-движка в Flutter нет. Полное совпадение каждой точки, размеров и анимаций пока не подтверждено.
Браузер используется для Google, внешней оплаты, Telegram и Swagger.

## Денежные операции

Перед покупкой сервер отдаёт точную цену. Подтверждённая цена отправляется вместе с заказом:
при изменении цены списание отклоняется. Расчёты выполняются Decimal/целыми микро USD.
До отправки сохраняются тело операции и случайный Idempotency-Key в защищённом хранилище.
Если ответ потерялся, клиент восстанавливает тот же запрос, используя тот же ключ.
Новая покупка требует сначала проверить незавершённую операцию. Неполная корзина показывает,
сколько пакетов оформлено и какая ошибка остановила остальные. Повтор не списывает за них дважды.

Списания, возвраты и выдача используют оригинальный `orders.py`, поставщиков и worker.
Если поставщик не поддерживает безопасный повтор, исходная логика направляет неопределённый
заказ администратору. Неопределённый результат не объявляется успешной выдачей.

## Запуск существующего сервера

Если рабочий сервер заказчика уже существует, его БД и настройки используются дальше.
Из корня этого комплекта:

```bash
python3 server_patch/apply.py /ПУТЬ/К/ПРОЕКТУ --check
python3 server_patch/apply.py /ПУТЬ/К/ПРОЕКТУ
```

После установки обновить Python-зависимости в **существующем venv сервера**:

```bash
/ПУТЬ/К/VENV/bin/pip install -r /ПУТЬ/К/ПРОЕКТУ/donatix/requirements.txt
```

Затем перезапустить существующий сервис Donatix. Проверить `/api/v1/mobile/config`
(должен вернуть `version: 4`) и `/api/v1/mobile-session` (401 до входа).
Установщик проверяет исходную ревизию всех изменяемых модулей и сохраняет предыдущий код. Обновление установленных версий 2 и 3 поддерживается;
каждый откат возвращает предыдущую версию, включая её резервную копию.
Незнакомую ревизию он не перезаписывает. Откат:

```bash
python3 server_patch/apply.py /ПУТЬ/К/ПРОЕКТУ --rollback
```

В ZIP не были переданы действующий файл серверных настроек, БД клиентов, ключи поставщиков
и upload-keystore Android. Они не могут быть восстановлены из исходного кода. Для существующего
сервера их не нужно переносить в телефон: приложение использует тот же сервер и те же аккаунты.

## Чистый сервер Ubuntu 22.04 / 24.04

В комплект включён весь сервер, отдельно скачивать исходники из GitHub не нужно:

```bash
cd Server
sudo bash donatix/deploy/install-local.sh
```

Скрипт установит Python, nginx, HTTPS, сервис и резервное копирование, скопирует локальный код.
При первом запуске он спросит домен, email/пароль администратора и настоящий ключ FazerCards.
Это реквизиты владельца сервиса. Подключения CoinDrop, Vendoria, Google, банков, крипты и Telegram
используют исходные настройки и инструменты `donatix/deploy/`; они включены в комплект.
Скрипт не был запущен на настоящем сервере в этой сессии.

Производственная проверка не допускает mock, временный SECRET_KEY, HTTP, выключенный worker
или незащищённую cookie. Для запуска вручную после настройки:

```bash
cd Server
python3 -m venv .venv
.venv/bin/pip install -r donatix/requirements.txt
.venv/bin/python -m donatix.production check-config
.venv/bin/python -m donatix.production serve --host 127.0.0.1 --port 8000
```

Google требует существующих `DONATIX_GOOGLE_CLIENT_ID`/`DONATIX_GOOGLE_CLIENT_SECRET`
и web redirect `https://ВАШ-ДОМЕН/auth/google/callback`. Новый секрет Google в приложении не нужен.

## Android-сборка

Flutter 3.35.4, Java 17, Android SDK 36. `compileSdk` и `targetSdk` явно равны 36.
Flutter-зависимости закреплены в `pubspec.lock`. Если используется другой домен,
заменить DONATIX_URL в команде и workflow:

```bash
cd Donatix_Flutter
flutter pub get
flutter analyze
flutter build apk --debug --dart-define=DONATIX_URL=https://ВАШ-ДОМЕН
```

Для коммерческого APK/AAB нужен **ключ владельца**, который будет использоваться для обновлений.
Заполнить `android/key.properties` по `key.properties.example`; секретный файл и keystore исключены
из git. Release не подписывается debug-ключом. После настройки:

```bash
flutter build apk --release --dart-define=DONATIX_URL=https://ВАШ-ДОМЕН
flutter build appbundle --release --dart-define=DONATIX_URL=https://ВАШ-ДОМЕН
```

В Codemagic подключить собственный приватный репозиторий. Если корнем является весь комплект,
использовать корневой `codemagic.yaml`; если только `Donatix_Flutter`, использовать файл внутри
этой папки. Workflow `android-check` собирает APK для приёмки. Для `android-release` добавить
keystore владельца с reference `donatix_upload`. Workflow не публикует приложение автоматически.
Ни один из этих workflow ещё не запускался в данной сессии.

## Проверки перед передачей заказчику

Выполненные проверки и оставшиеся условия перечислены в `RELEASE_STATUS.md`.
Сначала нужен успешный APK/AAB и запуск на телефоне: регистрация, восстановление входа,
фото/PDF, выключение/возобновление, реальный согласованный заказ, выдача/возврат,
дублирование на плохой связи, права администратора, графики, экспорт и уведомления.
Затем требуется сравнение экранов с исходным сайтом и закрытый тест Google Play.

Удаление аккаунта и связанных данных добавлено в этот комплект: в приложении и на
`/account-deletion`. При незавершённых расчётах аккаунт блокируется и ожидает возврата/
завершения операций; деньги не обнуляются автоматически. Затем выполняется удаление.
Перед Play-релизом владелец должен утвердить политику хранения, проверить резервные копии
и модель платежей для своего каталога и стран. Материалы подготовлены в `Play_Market/`.
Исходные внешние платежи сами по себе не означают разрешение Google Play.

Официальные требования и инструкция CI:

- https://support.google.com/googleplay/android-developer/answer/11926878
- https://support.google.com/googleplay/android-developer/answer/13327111
- https://support.google.com/googleplay/android-developer/answer/9858738
- https://docs.codemagic.io/yaml-basic-configuration/yaml-getting-started/
